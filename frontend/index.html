Module 0 — Kickoff

15 min  |  Concept overview — no code written by participants yet.

The Physical AI pipeline

Physical AI is the discipline of building systems that perceive the physical world through sensors, reason about that world, and act on it through actuators — closing the loop between sensing and doing.

Every module today builds one piece of this pipeline. By Module 4, the full loop is closed: your hand gesture changes the simulation, which changes what the next frame looks like.

[Webcam] → [Perception Layer] → [State Vector] → [Sim Agent] → [Action] ↑ ↓ [World/Sim] ←───────────────────────────────────────────────── [Effect] ↑ [Foundation Model Reasoning]

The loop is closed: every action changes the simulated world, which changes what the camera sees next. This closed-loop property is what distinguishes Physical AI from static inference tasks.

The state vector

The state vector is the central data structure of the pipeline — a compact numeric array that encodes everything the agent needs to know about the world at one instant. It bridges perception (raw sensor data) and control (the action the agent takes).

Module 1 — Perception

How perception works

A camera frame is processed by MediaPipe's Hand Landmarker model, which returns 21 normalised landmark coordinates per hand. From three pairs of landmarks we compute a joint angle using a dot-product formula, producing a compact state vector the rest of the pipeline can act on.

Everything in this module runs entirely in the browser — no server needed. The MediaPipe WASM bundle and model are loaded from CDN on first use.

Landmarks used for joint angles:

θ_index lm0 → lm5 → lm6
θ_middle lm0 → lm9 → lm10
θ_ring (exercise) lm0 → lm13 → lm14
θ_thumb lm0 → lm1 → lm2
lm8 tip used in Module 4
Angle formula
θ = atan2(|u × v|, u · v)

u = lm_base − lm_vertex, v = lm_tip − lm_vertex. Returns the opening angle at the MCP joint in degrees (0° = closed, ~180° = fully open).

Module 2 — Simulation

20 min  |  Gymnasium environments, observation and action spaces, Reacher-v5.

What is a simulation environment?

Gymnasium wraps physics simulations behind a standard interface. Every environment exposes two key objects:

Observation space — what the agent sees

A numpy array of floating-point numbers describing the world state at each timestep. For Reacher-v5 (10 values):

  • obs[0,2] — cos/sin of shoulder joint angle
  • obs[1,3] — cos/sin of elbow joint angle
  • obs[4,5] — target x, y position
  • obs[6,7] — joint angular velocities ω₁, ω₂
  • obs[8,9] — fingertip−target vector (distance = norm(obs[8:10]))

This is exactly what you see in the data panel of the simulation stream above — live values from the running environment.

Action space — what the agent can do

For Reacher-v5: a 2-element float array in [−1, 1]. Each value is a torque applied to one joint. Positive torque rotates clockwise; negative rotates anticlockwise. The sliders below let you apply these torques interactively.

Why use cos/sin instead of the angle directly? Angles wrap around — 359° and 1° are numerically far apart but physically adjacent. Representing angle θ as (cos θ, sin θ) removes the discontinuity and makes learning much easier.

Module 3 — Reinforcement Learning

30 min  |  MDP concepts, PPO training, live reward chart.

What is reinforcement learning?

RL is a trial-and-error loop. An agent observes the world, takes an action, and receives a reward signal. Over many episodes it learns which actions lead to more reward. No labelled data — just feedback from the environment.

The MDP — Markov Decision Process

Every RL problem can be written as a 4-tuple (S, A, R, γ):

  • S — State space: everything the agent can observe (e.g. the 4 CartPole values)
  • A — Action space: everything the agent can do (e.g. push left or push right)
  • R — Reward function: +1 every timestep the pole stays upright; 0 on failure
  • γ — Discount factor: how much the agent values future rewards vs. immediate ones (0 = greedy, 1 = patient)

The "Markov" property means the current state contains all the information needed — no memory of previous states required.

Policy, value function, and PPO

A policy π(a|s) is a mapping from state to action probabilities — it is what the agent learns.

PPO (Proximal Policy Optimisation) updates the policy in small, safe steps. It computes an advantage estimate (how much better an action was than expected) and clips the update to prevent catastrophically large policy changes. Same algorithm used in real robot controllers at scale.

What to watch for in the chart: The reward curve stays flat at first (random exploration), then rises sharply. That inflection point is when the agent discovers the balancing strategy. If you train for too few steps, it never finds it.

Module 4 — Perception to Action

40 min  |  Hand gestures drive Reacher joint torques — the full sense–plan–act loop.

Closing the loop

This module wires together everything from Modules 1 and 2. Your hand position becomes the action sent directly to the MuJoCo environment — no learned policy, just a direct mapping.

Landmark → action mapping

MediaPipe returns landmark 8 (index fingertip) as normalised coordinates in [0, 1]. The Reacher action space expects torques in [−1, 1]. The mapping is a simple linear stretch:

action = 2 × landmark_x − 1

Move your finger from left to right: torque goes from −1 to +1. Up/down maps to the second joint. That's it — the entire "brain" in this module is two lines of maths.

Teleoperation and imitation learning

What you're doing here is teleoperation — a human directly controls a robot's actuators through a sensory interface. This is how large demonstration datasets are collected for imitation learning algorithms like Behaviour Cloning (BC), ACT, and Diffusion Policy.

The key insight: the same physical setup — camera + landmarks + action mapping — that you're using interactively today is used in real robotics labs to collect thousands of demonstrations that train production robot policies.

Torque ≠ position. You're commanding force, not target angle. The arm overshoots and corrects because of inertia. This is why the arm keeps spinning when you hold the slider at full torque — there's no position controller, only continuous force application.

Module 5 — Foundation Models

25 min  |  Camera frames sent to Gemini, structured robot action suggestions returned.

Vision-Language Models for robotics

Large language models can read images. A Vision-Language Model (VLM) accepts both text and images as input and produces text as output. For robotics, the key insight is: if you prompt the model with an image of the robot's workspace and ask for a structured action, you get a zero-shot robot controller — no training required.

The Vision-Language-Action (VLA) pattern
  • Capture: grab one camera frame as a JPEG
  • Encode: convert to base64 — the format the API accepts
  • Prompt: send frame + text instruction to the model
  • Parse: extract structured JSON from the response
  • Act: map the JSON action field to robot commands

This is exactly the pattern used in production VLA systems like RT-2, OpenVLA, and π0 — just at much larger scale and with fine-tuned models.

Why prompting matters

The model has no world model for your specific robot. The system prompt defines the entire action vocabulary, output format, and reasoning context. A poorly written prompt produces unstructured or hallucinated outputs. A good prompt constrains the model to return exactly the JSON your parser expects.

{"action": "LEFT|RIGHT|FORWARD|BACK|WAIT", "reason": "one sentence"}
No API key? Pre-cached responses load automatically and the exercise still runs. You'll see the same JSON structure as a live response, but the text came from a static dataset — the model is not analysing your camera frame. The response will include "_source": "cache" to make this visible. Add a key above and use a live camera frame for real inference.

Sim-to-real transfer

Policies trained entirely in simulation — like the PPO agent from Module 3 — can be deployed on real hardware if the simulation is faithful enough to the physical world. The gap between simulated and real dynamics (the sim-to-real gap) is narrowed by domain randomisation: training across randomised mass, friction, and sensor noise distributions so the policy generalises rather than overfitting to one set of physics parameters.

Digital twins take this further — a continuously updated high-fidelity simulation that mirrors a specific physical asset in real time. Sensor readings from the real robot are fed back into the simulation to keep it synchronised, enabling safe policy evaluation and predictive maintenance without touching the hardware.

What to explore next

  • Isaac Lab — NVIDIA's GPU-accelerated robot learning framework built on Isaac Sim; runs thousands of parallel MuJoCo-quality environments for fast sim-to-real transfer.
  • LeRobot — HuggingFace's end-to-end imitation learning library; the natural next step after Module 4's teleoperation, turning your demonstration data into a trained Diffusion Policy or ACT policy.
  • ROS 2 — the Robot Operating System; the industry-standard middleware for connecting perception, planning, and actuation nodes on real hardware across a distributed network.
